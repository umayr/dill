# Lifecycle failures and compatibility

`down`, `stop`, `rm`, `teardown`, and orphan removal report resource-scoped failures and return a nonzero status instead of treating partial cleanup as success. Independent resources are attempted where possible. A failed stop is reported even if the subsequent remove succeeds; a failed remove identifies a resource that may be retained. Existing `rm` and `teardown` confirmations remain. Existing scripts that relied on a zero exit status after failure must handle the nonzero status. Starting an existing container reports start failures even when a later readiness check might have succeeded; the engines' explicit already-running response remains idempotent.

Container mutations use inspected or newly created IDs. Cleanup after a failed deployment uses a fresh bounded context, reports both the original failure and cleanup failures, and is not restoration or rollback. If cancellation is observed as a readiness response arrives or after the final readiness check before deployment completes, the deployment fails and cleanup is attempted rather than reporting success. A failed or cancelled create may have reached the engine without returning an ID; its outcome is unknown and the named resource may remain. Inspect before retrying. This change does not restore replaced containers or application data.

Docker and Podman network deletion is disabled: both engines can resolve an ID-shaped deletion target as a network name, so the inspected ID alone cannot ensure safe deletion after concurrent replacement. Existing networks are retained and reported as an error; absent networks remain idempotent. This changes full down and teardown behavior: after verifying ownership and preventing concurrent changes, operators must remove retained networks manually. Teardown resolves image IDs before deletion and reports image inspection failures or responses without an ID rather than treating the image as absent; `--force` remains destructive for shared images. Both engines retain existing named volumes and return an error, even with `--force`: their APIs identify volumes by reusable names and cannot condition deletion on immutable identity. This is a compatibility change: teardown no longer deletes stack-owned volumes, so operators must verify ownership and prevent concurrent changes before manually removing them. Already-absent volumes are treated as success; foreign or changed ownership and inspection failures are reported.

These resource-scoped Go errors and human-readable diagnostics are internal, not a stable JSON protocol. Versioned machine-operation results, durable outcomes, cross-process locks, reverse-DAG lifecycle ordering, and full recovery are deferred to #19, #42, #11 and #43. Independent cleanup does not imply a transactional deployment. Concurrent external modifications remain possible; image and volume resources have shared-engine semantics.
