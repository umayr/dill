# Lifecycle failures and compatibility

`down`, `stop`, `rm`, `teardown`, and orphan removal report resource-scoped failures and return a nonzero status instead of treating partial cleanup as success. Independent resources are attempted where possible. A failed stop is reported even if the subsequent remove succeeds; a failed remove identifies a resource that may be retained. Existing `rm` and `teardown` confirmations remain. Existing scripts that relied on a zero exit status after failure must handle the nonzero status.

Container mutations use inspected or newly created IDs. Cleanup after a failed deployment uses a fresh bounded context, reports both the original failure and cleanup failures, and is not restoration or rollback. A failed or cancelled create may have reached the engine without returning an ID; its outcome is unknown and the named resource may remain. Inspect before retrying. This change does not restore replaced containers or application data.

Network deletion requires Dill ownership labels and targets the inspected ID; legacy or shared networks without those labels are retained with an error. Teardown resolves image IDs before deletion; `--force` remains destructive for shared images. Both engines recheck `dill.managed` and `dill.stack` immediately before deleting a named volume. The engine APIs identify volumes by reusable names and do not offer conditional deletion by immutable identity: a volume replaced between that recheck and deletion can still be deleted. Operators must prevent concurrent external volume mutations during teardown. Already-absent volumes are treated as success; foreign or changed ownership and engine failures are reported.

These resource-scoped Go errors and human-readable diagnostics are internal, not a stable JSON protocol. Versioned machine-operation results, durable outcomes, cross-process locks, reverse-DAG lifecycle ordering, and full recovery are deferred to #19, #42, #11 and #43. Independent cleanup does not imply a transactional deployment. Concurrent external modifications remain possible; image and volume resources have shared-engine semantics.
