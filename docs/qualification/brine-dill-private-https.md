# Released Brine + Dill private HTTPS qualification

**Proposed procedure; runtime qualification NOT RUN.** Use the [evidence template](brine-dill-evidence.md) for each run. A release listing, CI smoke test, local syntax check, or green Brine page is not paired runtime evidence.

## Profile and release gate

- Two disposable native Linux hosts (Brine and target), one operator, one Brine instance, one Dill agent, and an independent local Docker daemon/socket on each host. Use Linux amd64 or arm64 without emulation; record the architecture, distro, kernel, Docker version, and daemon identity of each host. No shared or production engine, Docker Desktop/Colima/Podman, engine proxies, SSH agent forwarding, Git automation in the core profile, or local Alpha. Connect the browser to authenticated Brine over private HTTPS (TLS reverse proxy, `--secure-cookies`, backend not externally reachable). Brine connects **directly** to the Dill agent on a separate literal private IP:port using the pinned leaf and signed binding; do not replace that leg with a terminating proxy. Limit both listeners to intended peers; never expose a Docker socket over the network. Keep the Brine-side Docker socket on its own disposable host; it grants host-level access.
- Pin the [Brine v0.1.1 image](https://github.com/umayr/brine/releases/tag/v0.1.1) to index digest `sha256:72ac691e8998c18a91b98c6a95f50bd8bf676109529593e6356de34e5430c5aa`; verify the matching platform manifest, OCI revision `290841901fcd8677b306940997a896b768fe6cb6` from the [successful release run](https://github.com/umayr/brine/actions/runs/44682137552), image used by the container, and `brine --version`. Record bundled `dill version` and `pkl --version` from the image (expected v0.8.1 / 0.31.1); these do not identify the target executables.
- Target pair: [Dill v0.8.1](https://github.com/umayr/dill/releases/tag/v0.8.1). For the in-place **agent upgrade** use [Dill v0.8.0](https://github.com/umayr/dill/releases/tag/v0.8.0) → v0.8.1 with the same pinned Brine throughout. For each target binary, compare `sha256sum` to the release API asset `digest` for `dill-linux-<arch>` before executing and record `dill version`. Verify the native Pkl 0.31.1 binary against the [Dill release toolchain manifest](https://github.com/umayr/dill/blob/v0.8.1/internal/loader/pkl-toolchain.json) (`pkl-linux-aarch64` for arm64), then check `pkl --version`. Do not substitute a source build, an unverified tag, or `latest`.
- **Historical release behavior only:** B2 exercises the released shared bearer: enabling the write routes on the agent gives the existing paired bearer write authority. That is not separate write enrollment or acceptance of [Dill #141](https://github.com/umayr/dill/issues/141), and must not be carried forward as a fallback. Do not enable B2 on any listener reachable by a monitoring-only client. Reader permissions after write opt-in, explicit write grants, rotation, and revocation belong to a separate #141 qualification.
- **Publication evidence only:** GitHub lists Brine v0.1.1 with the index digest above and both Dill releases with native Linux asset digests. Brine's [v0.1.0 release job](https://github.com/umayr/brine/actions/runs/44678242207) failed the smoke step before the tag-and-release step; a Git source tag alone is not an eligible predecessor image. A **Brine image version upgrade** needs two independently verified published images; mark U3 `BLOCKED` until that pair exists. Recreating v0.1.1 with existing state is a restart test, not U3.

## Before touching the lab

- Record the lease/expiry, operator, resource prefix, bounded fault and recovery windows, and ownership of both hosts. Require fresh private roots, a clean target, and no competing writers or auto-deploy/pull/prune jobs. Check the effective Docker sockets, daemon IDs, host/network isolation, and absence of the selected names and ports. For Docker observations on the target, set `Q_DOCKER` to the independently verified `unix:///...` endpoint; pass `--host "$Q_DOCKER"` explicitly. Compare `docker --host "$Q_DOCKER" info --format '{{.ID}}'` to the agent's enrolled daemon ID. Use the same endpoint on every probe; don't inherit a default context.
- Provision a persistent private Brine `/data` mount and private remote registry, both visible to the one Brine process. Follow the [tagged Brine setup](https://github.com/umayr/brine/blob/v0.1.1/README.md#remote-hosts): initialize the registry once in the same mounted location, start with `--remote-enabled`, its explicit registry path, a positive `--remote-timeout` (start with `10s`), and authentication. Restrict the upstream bind/publish to the reverse proxy; never use `--no-auth`. Follow the [tagged Dill agent guide](https://github.com/umayr/dill/blob/v0.8.1/docs/host-agent-https.md): initialize HTTPS once and run the combined `dill agent` with the explicit native Docker socket, enrolled engine ID, observed daemon ID, stable generation, and private listener. Use distinct durable private staging, catalog, coordination, and apply-history directories with trusted ancestors. Pass `--https-staging-root`, `--https-staging-catalog`, `--https-preview-state`, `--https-preview-pkl`, and `--https-apply-state` for writes. Keep engine and filesystem identities fixed across restarts. Run the agent under supervision that can stop the entire dedicated process group/cgroup, including the checked child, without touching Docker.
- All provisioning and credential handling belong to the future lab operator. Keep pairing data, proxy keys, auth, and state private; no values in commands, notes, shell traces, logs, or evidence. Compare the TLS pin, signing identity and engine binding out of band before enrollment. Do not attach raw headers, HAR files, raw logs, or registry/journal dumps. Use the [evidence rules](brine-dill-evidence.md#evidence-handling).
- Preload a pinned native BusyBox image on the target (`busybox@sha256:<verified digest>`); verify its `httpd`, `wget`, shell and `sync` applets before any fault test. Pick a predeclared readiness budget (e.g. 60 s) and an operation/status budget (e.g. 6 min; the agent bounds checked execution to 5 min). Take before/after inventory and bounded events for each case, including outages. Record exact local IDs privately and use stable aliases in the handoff. Query container identity and mount source/destination, network ID, volume name/driver/labels and actual canary bytes; a name or label alone is not a data oracle. Record the collector start/end time and any coverage gap; Docker events alone are not a complete audit log.

Example target probes (set `Q_STACK` to the synthetic stack name; inspect only verified synthetic objects):

```sh
cat /proc/sys/kernel/random/boot_id
docker --host "$Q_DOCKER" ps -a --no-trunc --filter "label=dill.stack=$Q_STACK" --format '{{.ID}} {{.Image}} {{.Status}}'
docker --host "$Q_DOCKER" container inspect --format '{{.Id}} {{.Image}} {{.State.StartedAt}} {{.RestartCount}} {{.HostConfig.RestartPolicy.Name}} {{json .Mounts}}' "$Q_CID"
docker --host "$Q_DOCKER" network inspect --format '{{.Id}} {{.Name}}' "$Q_NETWORK"
docker --host "$Q_DOCKER" volume inspect --format '{{.Name}} {{.Driver}} {{json .Labels}}' "$Q_VOLUME"
```

Derive `Q_CID`, `Q_NETWORK`, and `Q_VOLUME` from the independent observations, not from guessed names. Treat `inspect` failure as missing evidence unless independently explained (such as verified absence before create). Use a concurrent bounded `docker --host "$Q_DOCKER" events` collector spanning the step rather than trusting a post hoc event lookup; include unexpected or unlabelled changes in the before/after inventory.

## Repeatable fixture

Create a Brine project whose name matches `config.name`, unique to each case or case chain, using only `compose.pkl` and `dill.pkl` with `compose.pkl` as entrypoint. Vendor the exact [v0.8.0 schema file](https://github.com/umayr/dill/blob/v0.8.0/dill.pkl) into this two-file fixture so the upgrade uses identical input; the v0.8.0 and v0.8.1 schema files are identical. Verify its bytes against the release tag; record both source hashes. Use the code below, replacing the stack name with the case-specific name and the image digest with the selected native image digest. The stateless variant removes the `volumes` line and changes `/data` to `/tmp` in the command. For a stateless update, add a second named service with the same image and command, no mount or published ports. Use a fresh project/stack for each independent create or destructive fault case; reuse the same project within its chain.

```pkl
amends "dill.pkl"

config {
  name = "qual-data"
  engine = "docker"
  services {
    ["web"] {
      image = "busybox@sha256:REPLACE_WITH_VERIFIED_DIGEST"
      pullPolicy = "never"
      restart = "unless-stopped"
      volumes = List("data:/data")
      command = List("httpd", "-f", "-p", "8080", "-h", "/data")
    }
  }
}
```

After observing a successful create and verifying the sole intended workload's full container ID (`Q_CID`) and `/data` mount, seed once and read using the app interface inside that container (no published app port). Replace `RUN_ID` with the synthetic run ID; compare the served bytes/hash to the expected marker **without reseeding** after each transition.

```sh
printf 'qual-RUN_ID\n' | docker --host "$Q_DOCKER" exec -i "$Q_CID" sh -c 'umask 077; cat > /data/marker.txt && sync'
docker --host "$Q_DOCKER" exec "$Q_CID" wget -qO- http://127.0.0.1:8080/marker.txt
```

The seed is the sole fixture data write; the intended Brine/Dill path is the only stack writer. Use the explicit restart/kill actions below only on the named lab process or canary. No CLI apply, direct Docker recreation of a managed workload, or retries to make a row pass.

For remaining branches, report separately (not implied by a core pass):

- **C3 — target-host outage during an admitted update (parked):** separate from C2 (agent-only interruption during create) and B4 (idle reboot). Would require a fresh stateless chain with a known successful create and an eligible update, unchanged Brine, proof that the exact update was admitted and still in flight when the whole target host (OS, Docker, agent) went down, and out-of-band proof the same host/storage returned with a new boot ID. A proven interrupted pending request should remain `unknown / unknown` and block writes; do not infer that from a timeout. Do not call a same-image restart an upgrade. Preserve the running journal; no downgrades or restoring old state in place.
- **G1 — Git fence/retry extension:** if separately authorized on a synthetic root-level read-only Git source and fresh lab stack, use the [released remote Git procedure](https://github.com/umayr/brine/blob/v0.1.1/docs/remote-agent-https.md#recover-a-pending-git-request). Require same-ID durable `not-admitted / none`, no engine effects, cleared pending intent with automation disabled, and retained deduplication after restart. On explicit re-enable, the same commit must not deploy; only a new reviewed eligible commit can be attempted. A fence on an admitted request returns the existing result; it does not cancel. Do not push from this qualification or replay the original apply to test the fence; without the fixture/trigger, mark `BLOCKED` or `NOT RUN`.

## Stop, recover, and close

- Use the [released attended procedure](https://github.com/umayr/brine/blob/v0.1.1/docs/remote-agent-https.md#manual-deployment-and-removal) for stage/preview/approval. A preview, HTTP 200, disconnect, missing request (including 404), or an empty event sample is not proof of completion or non-admission. Observe the original request/status link, compare the target and actual effects, and stop at the predeclared deadline. Do not submit the original or a fresh write after an ambiguous upload or apply. `unknown`, `partial`, journal mismatch/capacity, and identity or data mismatches require escalation and preservation, not pruning, adoption, or state reset. A fresh eligible write is a separate reviewed action, never an automatic retry.
- Freeze each case's evidence before teardown. Keep unresolved chains quarantined; no managed removal on them. An authorized operator may separately exercise **Remove containers; keep data** on a completed, unambiguous data case, verifying the receipt plus retained volume/network and no container (retention is not a restore). Disposal is a separate, authorized lab action: verify exact hosts/resources, revoke disposable access as applicable, record the disposition/owner, and leave shared or unknown resources untouched. Do not use Docker-wide prune or delete state to regain eligibility.
- A pass covers only the identified tuple and exercised paths. Not covered: production, other engines, public HTTPS, credential rotation, backup/restore, named-volume migration, in-place downgrade, and optional branches unless run and recorded separately.
