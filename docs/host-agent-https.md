# Direct HTTPS host agent (experimental read-only)

Run one agent per Docker target. The standard `dill` binary includes `dill agent`, which accepts the same arguments as the standalone `dill-agent` shown below. This mode is an alternative to the private Unix agent listener and does not use SSH. The default HTTPS routes serve only session, inventory, inspect and logs. Staging, preview and checked stack creation each require additional local opt-in; removal and environment reveal are not available over HTTPS. Docker still uses an explicitly enrolled local Unix socket. Treat log and inspection output as potentially sensitive.

1. As the service account, run `dill-agent init-https --dir /absolute/new/credentials` under a trusted parent. This creates an owner-only directory with a TLS certificate/key, session signing seed, and unique bearer credential. Existing directories are never changed. If creation is interrupted, inspect the partial directory rather than reusing it blindly.
2. Start the agent with `--https-dir /absolute/new/credentials --https-listen <private-ip>:<port>` and the normal `--engine-socket`, `--engine-id`, `--daemon-id` and `--generation` enrollment flags. Supply a literal private address; apply host firewall rules for your network and keep the credential directory and all ancestors protected. Do not run a public listener or forward the Docker socket.
3. From a private local terminal, invoke the same command with `--print-https-pairing` appended. This prints one JSON bundle to stdout and exits without listening; **the output is a reusable secret**, not an expiring code. Copy it only through trusted local means, with the listener address entered separately in Brine. Do not log, paste into public support messages, or store the bundle in ordinary temporary files. The export records the configured engine binding; the signed session checks the actual daemon before Brine accepts it.

## Optional catalogued staging

Both `--https-staging-root` and `--https-staging-catalog` must point to distinct existing private roots to add `POST /v1/snapshots` and `GET /v1/snapshots/{id}` to the authenticated listener. Without those flags the routes are unavailable. Staging can store sensitive files, so enable it only when the Brine instance and roots are trusted. It uses the bounded [snapshot staging protocol](snapshot-staging.md) but does not expose `dill-serve` health/status. An ambiguous upload is not safe to retry automatically. Staging alone never evaluates the project, writes to Docker, or deploys it. There is no automatic removal or quota.

## Optional deployment preview (native Linux Docker)

With the combined `dill agent` entrypoint, supply `--https-preview-state` (the same private coordination directory used by the qualified CLI) and `--https-preview-pkl` (an absolute operator-managed Pkl executable), in addition to the two staging flags. Only enable this for **trusted projects and a trusted Brine instance**: preview evaluates Pkl with the agent account's privileges. This is not a sandbox. Do not expose deployment preview from a network where the bearer credential is not adequately protected.

Authenticated `POST /v1/deploy/preview` accepts exactly `stageId`, `manifestSha256` (the catalog's lowercase hex digest) and `stack`. The agent revalidates the published tree and runs its own binary's `dill preflight up` with the configured engine socket and daemon ID, shared coordination state, no-prune and already-present images (`pull never`). Client-supplied command, paths and overrides are not accepted. The successful response is the existing `dill.preflight/1` result. This preview may write coordination metadata but does not mutate Docker. It is not an approval. A listener with checked creation enabled advertises `X-Dill-Create-Enabled: 1` on the preview response.

## Optional checked creation and status

Add `--https-apply-state /absolute/private/operations` to the combined agent only when you want Brine to create stacks. It must be a separate existing owner-only directory, with trusted stable ancestors. Keep it and the shared CLI coordination state durable; never remove or recreate either to clear an uncertain outcome. One agent process owns the history directory. The retained 1,024-record bound fails closed rather than evicting evidence.

`POST /v1/deploy/apply` takes the exact preview's `stageId`, `manifestSha256`, `stack` and `selectionDigest`, a 32-character lowercase hexadecimal `requestId`, and `confirm: "create"`. It re-runs preflight, requires all selected resources to be absent, rechecks the snapshot, saves intent, and runs checked `dill operation up` with the same state as cooperating CLI callers. It never falls back to legacy `up`. Updates and adoption are not supported. The bearer credential grants creation when this flag is on; Brine provides the human confirmation boundary. Other clients with the bearer can submit their own confirmation.

`GET /v1/deploy/operations/{requestId}` observes a request without submitting it. A known result contains the request ID, stack, state, effects, and when available a validated Dill operation ID. A disconnect after durable admission does not request cancellation. Pending at process restart is `unknown`, never replayed; unknown or partial creation blocks another creation for that stack. `404` or a delivery failure does not prove absence of effects. Use an independently authorized inspection procedure for unknown outcomes; there is no automatic acknowledgement, retry, deletion or rollback. Direct engine access or an uncoordinated CLI is outside the cooperative locking guarantee.

## Credential lifecycle

TLS uses an independently shared SHA-256 pin of the leaf certificate and a separate bearer credential. The agent's signed read protocol still uses its own persistent signing key. Restarts keep host identity as long as the credential files are unchanged. To invalidate an old Brine credential, replace that target's private token through an authorized host operation and restart; coordinate re-pairing separately. Removing the target from Brine alone does not invalidate a copied token. The generated certificate is valid for five years; renewing it changes the pin and requires re-pairing. Protect the daemon socket separately; the agent's network credential is not a Docker credential.
