# Current-schema validation compatibility

This describes the checked-in `dill.pkl`, not the roadmap's future schema or a versioned operation protocol. `validate`, `plan`, `diff`, and `up` use evaluated configuration and offline runtime/graph validation before target access. Validation rejects unknown properties and duplicate JSON keys, invalid dependency graphs, reserved labels, malformed ports/mounts/resources and the checked healthcheck values. Modules emitting custom JSON are also checked for required services/image/probe values and engine, restart and pull-policy values. Evaluator process failures remain operational/evaluator failures, not inferred invalid input.

`networkMode` retains its legacy engine-native meaning. Managed namespace reference resolution and implicit dependency edges are explicitly deferred to #9; a `container:` value is not a Dill-managed graph reference. Offline validation is not a host safety policy or target capability check.

Invalid decoded input exits 2; operational/evaluator failures exit 1. Plan uses exit 1 for drift; diff returns 0 for drift; doctor returns 1 when checks fail. Structured output distinguishes evaluated invalid input and evaluator failure where command JSON rendering has started. Early global/command flag parsing, unsupported formats, and some pre-render failures do not promise JSON stdout; exit 1 alone does not distinguish drift from operational failure without the command/result context. No stable versioned machine protocol is claimed (#19).

Custom JSON decoding is not a complete independent implementation of every Pkl type constraint: Go zero values can still collapse some null or omitted optional/defaulted values, including elements in string collections. Pkl schema evaluation remains the authoritative type check when amending `dill.pkl`. Do not assume every arbitrary JSON-producing module or future schema is accepted or fully validated. Engine-specific names, capabilities and target state require later checks (#15, #40).
