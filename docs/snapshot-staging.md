# Experimental local snapshot staging

Opt in with `--staging-root /absolute/private/root`, an existing directory owned by the effective user with no group or other permissions. The root and **all its ancestors** must be trusted and protected from modification by untrusted users. Same-user processes are trusted. The private Unix socket is the sole authentication and authorization boundary: any process able to access it can stage files. This is a trusted local single-operator interface, **not proof of human review**. Brine must show the exact file list and obtain explicit confirmation before sending any bytes; this service cannot verify that consent. No evaluation, planning, deployment, secret delivery, remote execution, or other runtime action follows an upload.

Optionally add `--staging-catalog /absolute/private/catalog`, an existing distinct operator-owned private directory, to durably register each newly received stage's exact manifest before reporting success. Both roots, their ancestors, the filesystem and same-user processes must be trusted. A catalog registration error occurs after stage publication and is therefore UNKNOWN; the stage and any partial record are retained. Existing uncatalogued stages are not adopted. This option does not enable deployment, inventory, or cleanup. Without it, staging remains available but successful stages have no service-owned catalog record.

With a catalog, `GET /v1/snapshots/{stage_id}` revalidates its record and full stage, then returns `stage_id`, `manifest`, and `manifest_sha256`: the SHA-256 of the exact compact JSON bytes of the emitted `manifest` object, including field order. The metadata contains relative paths, lengths and content hashes, not file contents. Received files always use mode 0600 and directories mode 0700; modes are not part of the manifest. Health advertises `snapshot-manifest` only when configured. The endpoint shares staging's admission slot, caps its response at 4 MiB to accommodate the maximum escaped manifest, and returns unavailable rather than unverified data. Metadata and content hashes can themselves be sensitive and are available to socket-authorized clients. It neither evaluates the project nor authorizes deployment; external imports and target identity are not attested by the manifest.

With the staging option set, health adds `snapshot-staging`. Without it, health and status retain their original responses and POST fails closed. `POST /v1/snapshots` accepts `Content-Type: application/json` without parameters and no query. Example shape:

```json
{"schema":"dill.snapshot.v1","entrypoint":"main.pkl","files":[{"path":"main.pkl","bytes":"YWJj","length":3,"sha256":"ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad"}]}
```

Files are an exact ordered array. Paths are slash-separated portable relative paths validated by the receiver; entrypoint must exactly match a file. Bytes are standard padded base64, length is the decoded byte count, and SHA-256 is 64 lowercase hex characters. Unknown, duplicate or missing fields, invalid schema, invalid paths, collisions, wrong lengths or hashes are rejected. JSON bodies are limited to 24 MiB including base64 and JSON overhead; at most 1000 files, 255 directories including the root, 32 path components, 512 path bytes, 255 component bytes, 4 MiB per file and 16 MiB decoded total. One upload can run at once; concurrent uploads receive 429. Server read/write deadlines apply. A successful response is 201 with `status` set to `staged` and `stage_id` set to a 32-character opaque lowercase hexadecimal identifier. It never contains a filesystem path; errors do not include submitted paths or contents. Body and decoded data are held in memory within these bounds. Status operations have their separately documented resource limits.

**A timeout, disconnect or lost response has UNKNOWN outcome:** publication may already have succeeded even if the caller did not receive a response. Do not automatically retry. Operator inspection and reconciliation are required; this experimental manual interface provides no reconciliation API or idempotency guarantee, and the identifier is available only after a successful response. A retry can create another retained copy. A cancelled request receives a non-success response when still writable; cleanup failures also produce a fixed sanitized operator diagnostic even if the client disconnected.

Stages are private directories. An `.in-progress-` directory is incomplete; a `snapshot-` directory has been published with no-replace rename after validation, file syncing and bottom-up directory syncing. The publication parent is synced before success is returned. Durability depends on the operating system and filesystem honoring sync operations; this is not an atomic source snapshot. A crash can leave incomplete material, and a failed parent sync after publication is an unknown outcome: the entire published stage is retained for operator inspection, never automatically retried or cleaned up. Failures may require manual inspection if cleanup cannot finish. No successful stage is automatically deleted: active-use tracking, a quota, an inventory endpoint and a cleanup endpoint do not exist. The operator must monitor disk consumption and manually identify and clean up old or incomplete material only after ensuring it is not in use; deletion is not secure erasure. Stages may contain secrets and must remain protected. See [receiver details](project-snapshot-receiver.md).
