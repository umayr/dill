# Local project snapshot receiver (experimental primitive)

`internal/projectsnapshot` validates an already in-memory manifest and content and stages it locally. The primitive itself does not evaluate Pkl or deploy. The opt-in local HTTP integration and its serialization contract are described in [snapshot staging](snapshot-staging.md). Each entry supplies a slash-separated path, bytes and a binary SHA-256 digest; the entrypoint must exactly match a file. The caller must not mutate the snapshot concurrently.

The fixed per-receive ceilings are 4096 files, 256 distinct directories including the stage root, 32 path components, 1024 path bytes, 255 bytes per component, 16 MiB per file and 64 MiB total. Callers must also cap concurrent receives: per-receive limits are not a process-global file-descriptor or resource quota. All caller-supplied limits must be positive and no higher than these ceilings. Validation completes before creating a stage. Only printable ASCII paths are accepted; trailing spaces/dots, Windows-forbidden characters, Windows device basenames, `.git` in any case, empty and dot components, and case-insensitive file/directory collisions are rejected. Allowed spelling is preserved. Empty directories and file modes are not preserved.

**Compatibility:** Brine's builder currently permits Unicode and case-sensitive paths and takes caller-specified limits, so some otherwise valid builder output is rejected. A future sender must prevalidate against this receiver's policy and report incompatibilities *before* asking for confirmation; it must never silently omit or rename entries. Whole-project transfer requires Brine to display the exact file list and obtain explicit operator confirmation. This primitive neither requests nor proves that consent. It does not provide an atomic source snapshot or a sandbox.

Staging is implemented only on Linux and macOS; other platforms fail closed. The configured root must already exist, be an absolute clean path, be owned by the current effective user and have no group/other permissions. The final root component is opened without following a symlink. The operator must also ensure that the root and **all its ancestors** are trusted and cannot be modified or replaced by untrusted users, and that the filesystem enforces expected Unix ownership, permissions and descriptor semantics. Same-UID processes, privileged processes, mount manipulation and concurrent mutation of the root or staging tree are trusted; this is not isolation against them. Directories and files are created exclusively, relative to open directory descriptors, without following symlinks, with modes 0700 and 0600 respectively. A restrictive umask or filesystem error may prevent creation. Cleanup removes only recorded created entries, refuses identity replacements, and reports errors; if identity cannot be obtained or cleanup fails, manual inspection and cleanup may be necessary. An in-progress directory has a `.in-progress-` prefix; after all writes and checks succeed, a descriptor-relative no-replace rename publishes it under a `snapshot-` name. Unsupported no-replace operations fail closed. No cleanup is performed after successful return. A crash can leave an in-progress directory; it is not automatically removed and requires operator inspection. Files and then directories are synced bottom-up before publication, and the publication parent is synced before reporting success. A failed parent sync after rename produces an unknown outcome and leaves the published tree untouched for operator inspection; it must not be automatically retried or deleted. Persistence depends on the OS and filesystem honoring these sync operations. This does not produce an atomic source snapshot or authenticate the contents of a later-replaced stage.

Snapshots can contain secrets. The caller/operator is responsible for retention and eventual secure cleanup of successful stages and any reported partial remnants, using the same trusted-root and same-UID assumptions. Deletion is not guaranteed to erase data from storage, backups, or caches. Never log snapshot bytes or publish the stage. Hashes detect content corruption but do not authenticate the sender.
